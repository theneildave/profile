Organizing Context in a Multi-Agent Harness: How to Prevent Context Rot, Poisoning, and Token Spikes

Neil Dave (Databricks Certified • Claude Certified Architect CCAR-P) November 16, 2026 14 min read Advanced Practitioner Level
The Hard Reality in 2026: Prompt engineering is commoditized. The true engineering bottleneck in enterprise AI is Context Engineering. When naive multi-agent systems crash, it is almost never because the model lacks intelligence — it is because the orchestration harness allowed the context window to decay into a chaotic dump of unpruned terminal outputs, obsolete assumptions, and runaway token bills.

1. The 3 Silent Killers in Multi-Agent Orchestration

Every engineering team building autonomous multi-agent systems (using LangGraph, CrewAI, AutoGen, or custom Claude harnesses) starts with the same naive architecture: a central supervisor with a shared conversational state graph, delegating sub-tasks to specialized worker agents.

In simple two-turn demos, this works flawlessly. But once an agent attempts complex, real-world tasks — such as refactoring a legacy repository, executing a financial reconciliation audit, or debugging a distributed microservice — the system collapses at Step 6 to Step 10 due to three distinct failure modes.

Silent Killer #1: Context Rot (Attention Dilution)

A widespread myth in modern AI engineering is that 200,000-token or 1,000,000-token context windows eliminate memory constraints. In production, attention dilution begins well before capacity is reached.

As agents invoke tools (bash shells, file search, SQL queries, web scrapers), intermediate outputs flood the working memory. When the context exceeds 35,000 to 50,000 tokens of raw tool output, the model's effective reasoning degrades sharply. It experiences the "Lost-in-the-Middle" phenomenon: it forgets earlier safety guardrails, ignores formatting requirements, and hallucinates parameters for tools it successfully called two turns prior.

Context Rot Defined: The progressive degradation of an LLM's reasoning fidelity caused by the accumulation of uncurated tool outputs, terminal logs, and conversational noise inside the active attention window.

Silent Killer #2: Context Poisoning (The Cascading Hallucination)

While Context Rot is a quantitative decay, Context Poisoning is qualitative corruption. In a shared-state harness, Subagent A (e.g. an investigative code analyst) misinterprets a legacy docstring and writes a false assumption into the shared state.

When Subagent B (the planner) and Subagent C (the code generator) read this state, they treat Subagent A's hallucinated premise as ground truth. Rather than verifying the underlying reality, they compound the error. Within three steps, the entire multi-agent swarm is passionately optimizing a non-existent system.

Silent Killer #3: The Quadratic Token Bill Spike

In naive harnesses, every message, every tool payload, and every intermediate reasoning step is appended to an ever-growing prompt array that is resent to the API on every single LLM call. Across $M$ agents making $N$ turns, input token consumption explodes quadratically rather than linearly.

2. The Mathematics of Multi-Agent Token Explosion

Let us look at the actual mathematics governing agent token economics. Consider an enterprise task requiring $N = 10$ sequential tool execution steps across $M = 3$ coordinating agents (Supervisor, Researcher, Coder).

When subagents re-read the entire supervisor conversation, token consumption escalates at $O(M imes N^2)$. Across 1,000 production workflows, the economics diverge catastrophically:

1. The Session (Append-Only Event Store)

The Session records everything that happens: raw bash commands, multi-megabyte API payloads, execution stack traces, and agent deliberations. Crucially, the Session is never fed raw to the LLM. It exists purely for observability, human-in-the-loop auditability, and replay debugging.

2. The Harness (The Context Governor)

The Harness is the operating system between your durable logs and the LLM's context window. It intercepts every outgoing prompt and performs active context curation: truncating verbose tool returns, compacting completed steps into state assertions, and gating tool schemas.

3. The Execution Sandboxes

Agents do not execute side-effects in the shared environment. They run in firewalled sandboxes. When a subagent finishes, the harness extracts only the artifact (a unified code diff, a Boolean verification check, a 2-paragraph synthesis) and discards the intermediate runtime scratchpad.

Mode A: Isolated Mode (The Clean Slate)

In Isolated Mode, the subagent receives zero conversation history from the supervisor. It receives only:

  • The specific task objective.
  • The exact inputs required (e.g., target file path, query string).
  • A strict output JSON schema or markdown rubric.

When to use Isolated Mode:

  • Adversarial Review & Code Quality: If you pass the authoring agent's thinking trace to the reviewer agent, the reviewer inherits the author's blind spots. An isolated reviewer evaluates code with zero bias.
  • Independent Fact Verification: Fact-checking claims without supervisor framing.
  • Parallelized Web/Document Search: Searching 10 endpoints simultaneously without polluting the main session.

Mode B: Forked Mode (The Cached Branch)

In Forked Mode, the subagent inherits the supervisor's baseline state, but operates on an isolated write-branch. Any failed tool executions or throwaway investigations are confined to the fork and never pollute the parent tree.

Maximizing Claude Sonnet 5.5 Prompt Caching in Forked Mode: By structuring the parent conversation so that static instructions, schema declarations, and foundational codebase maps sit at the very beginning of the prompt array, you set Anthropic's cache_control: {"type": "ephemeral"} breakpoint. The subagent reads the parent context at 10% of normal input pricing with sub-second Time-to-First-Token (TTFT).

5. Production Compaction & Ephemeral Scratchpads

How do long-running autonomous workflows survive 50+ tool iterations without crashing? Through two core architectural patterns: Compaction Loops and Ephemeral Scratchpads.

The Compaction Loop

When a sub-task completes (e.g. running unit tests, inspecting 14 documentation files), the harness invokes a fast compaction prompt (using Claude 3.5 Haiku) that transforms 20 turns of back-and-forth into a single immutable observation:

[Agent]: Calls grep_search("verify_token")...
[Tool]: Returns 45 matches across 12 files...
[Agent]: Reads auth/jwt.py lines 1-150...
[Tool]: File contents...
[Agent]: Runs pytest test_auth.py...
[Tool]: FAILED (jwt.exceptions.ExpiredSignatureError not caught)
[Agent]: Edits auth/jwt.py line 48...
[Tool]: File written...
[Agent]: Runs pytest test_auth.py...
[Tool]: PASSED (12 tests passed).

# AFTER COMPACTION (112 tokens in active context):
[COMPACTED STATE ASSERTION - STEP 3 COMPLETED]:
• Bug Located: auth/jwt.py line 48 failed to catch jwt.exceptions.ExpiredSignatureError.
• Action Taken: Added explicit exception handler falling back to 401 Unauthorized.
• Verification: pytest test_auth.py passing (12/12 tests green).

Dynamic Tool Gating via Model Context Protocol (MCP)

Injecting 40 tool schemas into your root prompt consumes 6,000+ tokens on every single LLM call before the user has even typed a word. Worse, it increases tool selection ambiguity.

In a governed harness, tools are gated dynamically via MCP servers. The root supervisor only sees 4 meta-tools (delegate_task, read_system_state, ask_user, finalize_output). Deep execution tools (SQL executors, Kubernetes controllers, terminal runners) are only provided to specialized subagents inside their isolated sandboxes.

6. Reference Implementation: Python Context Governor

Below is a production-tested Python harness pattern demonstrating isolated subagent dispatch, ephemeral scratchpad execution, and Anthropic prompt caching headers:

import os
from typing import Dict, Any, List
import anthropic

client = anthropic.Anthropic(api_key=os.environ.get("ANTHROPIC_API_KEY"))

class MultiAgentHarness:
    def __init__(self, system_manifest: str):
        self.system_manifest = system_manifest
        self.session_log: List[Dict[str, Any]] = []

    def run_isolated_subagent(
        self, 
        task_instruction: str, 
        context_payload: str,
        output_schema: str
    ) -> str:
        """
        Executes a subagent in ISOLATED MODE.
        Context window contains zero supervisor chatter.
        """
        subagent_prompt = f"""You are a specialized verification agent.
CRITICAL CONSTRAINT: You operate in an isolated context. Focus strictly on your task.

TASK SPECIFICATION:
{task_instruction}

TARGET CONTEXT:
{context_payload}

REQUIRED OUTPUT FORMAT:
{output_schema}
"""
        response = client.messages.create(
            model="claude-sonnet-5-5-20261022",
            max_tokens=2048,
            temperature=0.0,
            messages=[{"role": "user", "content": subagent_prompt}]
        )
        verdict = response.content[0].text
        
        # Log complete execution to durable Session, but return only distilled verdict
        self.session_log.append({
            "type": "isolated_subagent_run",
            "task": task_instruction,
            "raw_verdict": verdict
        })
        return verdict

    def run_supervisor_step_with_caching(
        self, 
        compacted_history: List[Dict[str, str]], 
        next_instruction: str
    ) -> str:
        """
        Executes supervisor step with Prompt Caching anchored at static manifest.
        """
        # Anchor the static system manifest with ephemeral prompt caching
        system_block = [
            {
                "type": "text",
                "text": self.system_manifest,
                "cache_control": {"type": "ephemeral"}  # 90% discount on cache hits!
            }
        ]

        messages = []
        for item in compacted_history:
            messages.append({"role": item["role"], "content": item["content"]})
        
        messages.append({"role": "user", "content": next_instruction})

        response = client.messages.create(
            model="claude-sonnet-5-5-20261022",
            max_tokens=4096,
            system=system_block,
            messages=messages
        )
        return response.content[0].text

8. Frequently Asked Architectural Questions

Why can't I just use a 1-million token context window and feed everything in?

Large context windows are designed for high-capacity document retrieval, not multi-step reasoning. Empirical benchmarks show that reasoning fidelity and tool parameter accuracy drop sharply once an active prompt accumulates hundreds of unrelated conversational turns. Furthermore, quadratic token costs make 500k-token agent loops economically non-viable for production software.

How does LangGraph handle context compared to Anthropic multi-agent patterns?

LangGraph models state as an explicit graph schema where nodes mutate shared channels. While powerful, naive LangGraph implementations frequently append all tool messages to a shared list. Anthropic's multi-agent patterns emphasize hierarchical supervisor-worker architectures where workers are spawned as ephemeral subagents with strictly scoped prompts and return compact messages to the parent.

What is the best way to handle bash shell outputs that exceed 10,000 lines?

Never dump raw terminal stdout into the context window. Your harness should write tool output to an isolated file in the sandbox (e.g. /tmp/build.log) and return only: (1) Exit Code, (2) Execution Time, and (3) A head/tail excerpt of the first 10 and last 20 lines. If the agent needs to inspect failures, provide a grep_log tool to query specific error traces.

            "type": "isolated_subagent_run",
            "task": task_instruction,
            "raw_verdict": verdict
        })
        return verdict

    def run_supervisor_step_with_caching(
        self, 
        compacted_history: List[Dict[str, str]], 
        next_instruction: str
    ) -> str:
        """
        Executes supervisor step with Prompt Caching anchored at static manifest.
        """
        # Anchor the static system manifest with ephemeral prompt caching
        system_block = [
            {
                "type": "text",
                "text": self.system_manifest,
                "cache_control": {"type": "ephemeral"}  # 90% discount on cache hits!
            }
        ]

        messages = []
        for item in compacted_history:
            messages.append({"role": item["role"], "content": item["content"]})
        
        messages.append({"role": "user", "content": next_instruction})

        response = client.messages.create(
            model="claude-sonnet-5-5-20261022",
            max_tokens=4096,
            system=system_block,
            messages=messages
        )
        return response.content[0].text

8. Frequently Asked Architectural Questions

Why can't I just use a 1-million token context window and feed everything in?

Large context windows are designed for high-capacity document retrieval, not multi-step reasoning. Empirical benchmarks show that reasoning fidelity and tool parameter accuracy drop sharply once an active prompt accumulates hundreds of unrelated conversational turns. Furthermore, quadratic token costs make 500k-token agent loops economically non-viable for production software.

How does LangGraph handle context compared to Anthropic multi-agent patterns?

LangGraph models state as an explicit graph schema where nodes mutate shared channels. While powerful, naive LangGraph implementations frequently append all tool messages to a shared list. Anthropic's multi-agent patterns emphasize hierarchical supervisor-worker architectures where workers are spawned as ephemeral subagents with strictly scoped prompts and return compact messages to the parent.

What is the best way to handle bash shell outputs that exceed 10,000 lines?

Never dump raw terminal stdout into the context window. Your harness should write tool output to an isolated file in the sandbox (e.g. /tmp/build.log) and return only: (1) Exit Code, (2) Execution Time, and (3) A head/tail excerpt of the first 10 and last 20 lines. If the agent needs to inspect failures, provide a grep_log tool to query specific error traces.
